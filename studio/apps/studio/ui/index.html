Start with a profile

A profile is the single source for a release: modules, commands, signatures, branding, ports, key paths and rollout stage. Secrets never live in the profile, only their file paths.

One profile builds one release. Keys are referenced by file path and never stored in the profile.

Pick what the guard does. Switching a module on also switches on everything it needs.

Enable, rename and rate-limit every command. ! commands are answered by the client guard, @ commands by the server.

Cheat signatures by tool group (prefix of the id, e.g. OG-RCX-001 is RCX). Default keeps each signature's own action, Off drops the group, any action replaces it for the whole group. Client counts entries the guard can check; the rest is analysis data. Custom signatures: add another TOML file under Profile → Signature sources.

Like Gepard's GRF check, but made for patchers: every GRF in DATA.INI must be an approved version (size + table hash, plus the file hash in the background) or an allowed mod. Before patching: scan the patched client with “Keep previous versions”, roll out the server config, then patch. odin.grf and the competitive pack are added by the build itself.

Rolling out a new release

        
A new Studio version is a new OdinGuard release: guard, odin.grf and server module. Installing it changes nothing for your players or your servers by itself. Nobody is updated without you; players only get it when you patch it to them. In this order, so nobody is kicked:

        
    
          
  1. Read the notes above. They say whether the server module or the protocol changed.
    2. 
          
  2. Install the update and restart Studio. Open your profile.
    3. 
          
  3. Rollout tab → Keep the built release. This keeps the release your players have now as an accepted one, so they pass the server checks until they have patched.
    4. 
          
  4. Build the new release.
    5. 
          
  5. Server: copy the new conf and references of the build to the server (and the new server module, if the notes say so) and deploy.
    6. 
          
  6. Players: put the new client files into your master client and publish them with your patcher.
    7. 
          
  7. Later, when (almost) everybody has patched: remove the kept releases, or set the oldest release that may log in.
